# 02 编策划案

## 一、这一步要什么

把立项卡里的方向写成一份**能直接照着做**的策划案。

**进入条件**：立项卡已通过。
**退出产物**：策划案文件。
**合格线**：做 Demo 的人、写代码的人读完这份文件，不需要再回来问任何一个问题，也不需要自己编内容。

计划性的东西可以留在“待定”，但**框架不能缺、能写具体的地方必须写具体**。

## 二、策划案要包含什么

按顺序写。确实不适用的节次写“本关卡不涉及此内容”，不要为了凑格式硬写。

### 1. 关卡名

2–4 个备选，标注主推方向。备选可以分别侧重世界观代入感、玩法特色、传播记忆点。不超过 8 个字，避免生僻字。复刻类关卡若沿用原作名，要同时给出一个可传播的中文自拟名。

### 2. 核心亮点

3–5 点，每点说清“差异在哪里”和“为什么玩家会因此选这个关卡”。可以来自玩法创新、视觉风格、剧情体验、操作手感、社交互动、技术实现等维度。

### 3. 核心玩法

- **玩家在做什么**：一句话说清玩家一直在重复做的那件事。
- **操作方式**：移动、跳跃、攻击、技能、交互分别对应什么操作；键鼠、触屏、手柄各一套都要写。
- **胜负与重开**：怎么算成功、怎么算失败、能不能重开、重开后回到哪里。
- **单局时长**：一局多长时间；分几段，每段大概多久。
- **难度变化**：从开始到结束难度怎么变；有没有难度档位。

### 4. 规则清单（写法有硬要求）

每条关键规则都要能写成一条可判定的用例：“在什么状态下 → 玩家做什么 → 期望看到什么”。把结论分三类并标出来：

| 类别 | 含义 | 由什么验证 |
|---|---|---|
| **体验假设** | “这样会更好玩”这类主观判断，例如手感、节奏、爽感 | 用户试玩网页 Demo；不能写成自动化断言 |
| **可测试规则** | 能写成明确判定的事实，例如计分、胜负、冷却、碰撞边界、重开 | 直接转成验收用例；必须是确定性的 |
| **未知事实** | 依赖平台能力或真实环境、暂时没有依据的点 | 先查文档或做最小验证，缺依据就保持未定，不能靠猜 |

可测试规则要满足确定性：**不依赖机器速度、不依赖现实时间、不依赖偶然的一帧**；随机行为要能通过配置或入口复现。写不出确定性判定的“规则”，说明它还是体验假设。

每条规则还要写清**边界与异常**：数值上限、同时触发多个机关、反复触发同一开关、结算过程中玩家还在操作、玩家长时间不操作。这些是后面最容易出问题的地方，必须在设计阶段就给出期望行为。

### 5. 数值

**每一项都要给具体数字**，不允许“较高”“适中”“若干”“视情况调整”：

| 类别 | 必须给出的项 |
|---|---|
| 角色 | 初始血量、血量成长、移动速度、加速度、跳跃初速、最大连跳次数、受伤无敌时间、复活时间 |
| 技能 | 冷却、耗能、前摇、后摇、持续时间、生效范围、伤害倍率、可否打断 |
| 敌人 | 血量、攻击力、攻击间隔、攻击前摇、移动速度、索敌半径、脱战半径、受击硬直、掉落与掉落率 |
| 关卡 | 单局时限、各段预期耗时、失败判定条件、复活点数量与位置、评级阈值 |
| 经济 | 每次获取量、上限、消耗点、单位时间产出、达到满级所需次数 |
| 难度 | 每段难度系数、敌人数量与血量倍率、可选档位的具体差异 |

确需后续确定的，写成“暂定 X，依据是 Y，后续按 Z 调整”。

数值还要**自洽**：同一数值在多处出现时不能互相矛盾。输出前自查一遍算术关系（例如角色血量与敌人伤害的组合，能不能算出“几下会被打死”，且与设计意图一致）。

### 6. 世界观

- 关卡发生的背景；尽量与某个地区、事件、角色故事或传说产生关联。
- 交代时间线位置。
- 纯机制小游戏可以只写两三句，不必硬写。
- **复刻模式例外**：走复刻路线时可以只写“沿用原作世界观 / 无世界观设定”，不必强行塞入现有设定（见 `08_参考_平台与玩法.md` 第四节）。

### 7. 剧情脉络

- 章节结构、关键转折、主要冲突、结局走向。
- 对话风格要与角色口吻一致；涉及既有角色时贴合其性格与设定。
- 说明呈现方式：关卡内演出、角色对话、收集品文本等。
- 没有剧情就写“本关卡无剧情向内容，以纯玩法体验为主”。

### 8. 人物设定

- 列出涉及的主要角色、NPC、敌人或首领。
- 每个说明：定位、动机、技能特点、与世界观的关系。
- **额外补充**：说明每个角色在 2D 画面里的表现方式（引用哪类图片资产、用几何图形拼合、用文字符号表示等）。

### 9. 玩家能看到的所有文字（逐字成稿）

这是把策划案从“方向”变成“成品”的关键一节。没有逐字稿，后面就得自己编文案，语气和节奏都会走样。

- **对话逐字写出来**，不允许“此处主角表示惊讶”“NPC 会介绍规则”这类概述。格式：

```Plaintext
[场景：初次进入大厅]
[角色：派蒙｜表情：好奇｜动作：绕圈飞行｜音效：无]
派蒙：哇，这里比我想的……热闹多了？
派蒙：你看那边那个牌子，该不会是要我们排队吧？
[玩家选项 A]「先看牌子。」
[玩家选项 B]「直接过去看看。」
```

- 每条对话标：说话人、表情或状态、必要动作、是否播声音、是否等玩家点击。
- 分支对话要把**每个分支的后续**都写完整，不允许“其余分支同理”。
- **所有固定文案都要给原文**：开场引导、按钮文字、失败提示、重试提示、结算评语、评级称号、成就名与描述、物品名与描述、加载提示、教学气泡、确认弹窗。禁止写“按钮文字自拟”。

**表达红线**：任何出现在玩家眼前的内容，都不允许出现实现原理与创作者术语——不写控件、锚点、分包、信号、浮点数、自定义变量、存档字段。要表达“保存进度”就写“已保存当前游玩进度”。

### 10. 界面与场景

- **界面**：有哪些元素（血条、分数、倒计时、对话框、按钮、装饰等），每个元素用什么方式呈现，放在哪儿、占多大；给出相对位置与相对尺寸，方便直接换算。
- **场景**：整体风格、色调、光照、地标、可交互物件、叙事性细节。
- **层级与优先级**：谁在上面、谁会被点到；避免关键操作被挡住。
- 场景之间怎么过渡，视觉上如何保持统一主题又做出区分。

### 11. 图片素材清单

集中成一张表，覆盖界面、场景、角色、特效、装饰全部类别：

| 素材名 | 用途 | 大致尺寸 | 是否需要染色 | 关键词 |
|---|---|---|---|---|
| | | | | |

这份表要原样交给用户，请其按顺序提供编号。**本目录没有可检索的素材清单**，编号只能来自用户；用户给不出时，写明改用基本图形自绘近似表现。

### 12. 必须由用户在编辑器里选的配置项

代码自己生不出来的值，单独列一张表：

| 配置项 | 用途 | 怎么拿到 | 缺失时怎么办 |
|---|---|---|---|
| 控件名称与相对路径 | 找到界面上已有的元素 | 在编辑器里选中该元素，读它的名称 | 该功能停用，并在交付说明里写明 |
| 控件模板索引 | 创建新的界面元素 | 在「客户端控件模板」里读编号 | 该功能停用 |
| 图片资源（来源 + 编号，成对） | 显示图片 | 由用户提供，两个值成对记录 | 该功能停用 |
| 动效编号 | 播放做好的特效 | 在动效设置里读编号 | 不播特效，其余照常 |
| 音频编号 | 播放声音 | 在音频资源配置里读编号 | 不播声音 |
| 按键枚举 | 按键提示 | 从当前 API 文档逐字抄 | 不显示提示 |

**每一项都要写明“缺失时怎么安全停用”**，不能填一个随便的数字继续跑。

### 13. 分辨率逐行推演（必写）

默认多端 + 横屏，矩阵见 `00_主控与派单.md` 3.2。逐个界面元素走一遍矩阵，写明在每一行上的表现：

| 元素 | 电脑16:9 | 电脑21:9 | 手机16:9 | 手机19.5:9 | 手机4:3 | 手柄16:9 | 手柄21:9 |
|---|---|---|---|---|---|---|---|
| | | | | | | | |

**手机三列是硬性要求**：手机上能看到的全部内容，必须在每一列里都完整可见，不能被裁掉、被挡住、被挤出屏幕。电脑与手柄端只做等比放大或留边。同时给出安全区范围与靠近边缘的元素清单。

### 14. 游戏资源与成长

- 关卡内所有可获取、可消耗或可交易的资源（物品、货币、等级等）。
- 每种说明：获取途径、用途、消耗方式、是否需要存储或限制数量。
- 说明核心数值关系：伤害与血量的比值、资源获取速率、升级所需经验曲线。
- 说明后续增加难度或扩展内容时数值怎么调整。
- 资源系统简单就简要说明，不要硬凑。

### 15. 引导与教学

- 新手教学怎么展开，怎么让玩家在游玩中逐步理解规则。
- 按阶段拆：前 30 秒教基础操作，前 3 分钟让玩家体验到核心乐趣，之后逐步引入新机制。
- 教学方式可以是隐性引导或显性提示。
- 检查有没有玩家可能卡住的地方，针对性地设计提示。
- 每条教学提示都要给玩家实际看到的原文。

### 16. 不做项与待确认项

- **不做项**：这次明确不做什么，至少与立项卡一致。
- **待确认项**：确实需要用户拿主意的事，集中放在最后，写成用户能直接回答的问题；写清“缺什么、有哪几个选项、推荐哪个”。不要混在正文里。

## 三、写的时候守这几条

- **不给实现留猜想空间。** 凡是能写出来的都要写出来；不允许“参考原作”“同前”“此处略”“自行发挥”。
- **数字、名称、术语全文统一。** 同一个东西不能在不同章节换名字。
- **不要出现创作过程的痕迹**：不写“我决定采用……”“考虑到成本……”。理由可以集中放在一小节“设计说明”里。
- **不写实现方案**，但**代码目录与模块分工要写**（见 `04_编写Lua.md` 第四节），因为它会影响后面每一次改动。
- **长度服务于信息量**，不要为凑篇幅重复。

## 四、两种身份的差别

- **萌新**：严格按上面的节次顺序写，一节不缺；拿不准的地方放进“待确认项”，不要自己拍板。
- **大佬**：节次顺序可以按项目特点调整、可以合并，但**上面十六类内容一个都不能少**；可以自己补一节“技术倾向”说明希望的实现风格。

## 五、验收清单

* [ ] 核心亮点 3–5 点，每点都说了差异与理由
* [ ] 核心玩法能用一句话说清，且说明白玩家一直在重复做什么
* [ ] 键鼠、触屏、手柄三套操作都写了
* [ ] 每条关键规则都标了“体验假设 / 可测试规则 / 未知事实”
* [ ] 可测试规则满足确定性（不依赖机器速度、现实时间、偶然帧）
* [ ] 每条规则都写了边界与异常情况的期望行为
* [ ] 关键判定建立在状态或原生事件上，不靠“差几个像素”定义成败
* [ ] 数值全部是具体数字，且算术关系自洽
* [ ] 世界观、剧情、人物三节都有内容，或明确写了“不涉及”
* [ ] 对话与所有玩家可见文案都是逐字稿，没有概述、没有“自拟”
* [ ] 玩家可见文案里没有实现原理与创作者术语
* [ ] 界面元素给了相对位置与相对尺寸
* [ ] 图片素材清单覆盖全部类别
* [ ] 编辑器侧配置项单列成表，且每项都写了缺失时的停用方式
* [ ] 分辨率按矩阵逐行推演过，手机三列全部完整可见
* [ ] 游戏资源与成长、引导与教学两节都写了，或明确写了“不涉及”
* [ ] 不做项至少两条
* [ ] 待确认项写成了用户能直接回答的问题
* [ ] 全文没有“参考原作”“此处略”“自行发挥”这类留白
