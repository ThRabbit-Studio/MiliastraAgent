# 03 Demo 初审

> 本分册里凡是要对用户说的话（追问、索取、交付、汇报），都由沟通任务执行，见 `24_子代理_用户沟通.md`；执行本分册的子代理不直接联系用户。

## 一、这一步要什么

做一份**能玩的网页 Demo**，让用户先把它玩一遍，对着它提意见、定手感，然后把它冻结成后面写 Lua 的依据。

**进入条件**：策划案已通过。
**退出产物**：干净的、可试玩的网页 Demo + 用户试玩结论 + 冻结版本号。
**为什么这一步不能省**：这是写 Lua 之前**唯一一次**能把玩法、难度、节奏、手感调对的机会。代码写出来再改玩法，代价要大得多。

## 二、Demo 必须做到的

### 2.1 把所有游玩内容都做进去

**不是做一半给用户看个大概，而是把这次要做的玩法内容全部做实。**

必须覆盖：

- 从开局到结束的**完整一局**；
- 策划案里**每一条可测试规则**都能在 Demo 里被验证到；
- 所有界面：开始、游戏进行中、成功、失败、重开，以及策划案里有的暂停、结算、设置等其他界面；
- 关卡有分段或分关的，**每一段都要能玩到**；
- 玩家能看到的全部文字，按策划案的逐字稿放进去；
- 操作提示与即时反馈（得分、受伤、进度、状态变化）。

**允许简化，但要在两处写清**：哪些是最终形态、哪些是临时替代。简化只允许出现在美术与音效上，**不允许删玩法**。

### 2.2 不能露出开发工具

交给用户的这一份必须是**干净的成品样子**：

- 不显示参考线、九宫格、中心点十字、元素描边、量测数值；
- 不显示调试面板、日志窗口、状态数据、帧率、按钮 id；
- 不显示任何“这里是占位”“待替换”“调试用”的字样；
- 不显示内部文件名、路径、编号。

量测与调试用的东西**只能藏在一个默认关闭的开关后面**，并且：

- 交出去之前要**亲自打开看一眼确认是干净的**，不要凭“我记得关了”；
- 给用户的是干净状态的那一份，不告诉用户怎么打开调试；
- 交付说明里写明“给用户的版本已关闭全部调试显示”。

### 2.3 用户能直接打开、直接玩

- 给的是**能打开的文件路径**，不是截图。
- 打开就能看到开局画面与一句操作说明；
- 手机比例下完整可见，关键操作不被挤出屏幕。

## 三、可以借 Demo 顺手完成的两件事

Demo 同时承担两个内部用途，但**不能因此把调试内容露给用户**：

1. **量测取样**：元素的位置与大小只能从这份文件的真实量测结果里取，不允许手算估计。后面写代码时，每个控件的锚点、中心点、位置、尺寸都要能追溯到这次量测。
2. **开发依据**：冻结之后，Lua 版本以它为准。

量测结果整理成一张**锚定配置表**（模板与规则见 `09_参考_布局与锚点.md` 第七节），一行一个元素，至少包含：编号、区域、锚点（最小→最大）、中心点、相对尺寸、相对偏移、最小可读尺寸、备注。这张表是后面写代码时唯一的位置来源。
调试与量测的具体做法（探针、文件命名、九宫格锚点表）见 `09_参考_布局与锚点.md`。

## 四、怎么交给用户

发给用户的内容，萌新模式用大白话，照着下面说：

> 我做好了一个能玩的网页版，你可以先玩一下。
>
> 怎么玩：<一句话说操作>
> 目标是什么：<一句话>
> 怎样算赢 / 怎样算输：<一句话>
>
> 玩完告诉我：哪里别扭、难度合不合适、节奏是快了还是慢了、哪一刻没看懂。

同时说明三件事：

- 这版做了哪些内容、哪些是最终形态、哪些是临时替代；
- 和上一版（如果有）的差别；
- 希望重点感受什么。

**不要把 Demo 说成承诺**：说明它是玩法与观感的预览，最终在编辑器里的表现要以真实运行为准。

## 五、收集意见并处理

用户一定会同时给两类意见，分开处理：

| 意见类型 | 例子 | 怎么处理 |
|---|---|---|
| **玩法与手感** | 太难、太慢、反馈不明显、操作别扭、不知道要干什么 | 改 Demo → **请用户再玩一遍**确认；同时回写策划案与验收用例（规则变了先改用例） |
| **界面与观感** | 按钮太小、字看不清、被挡住、颜色不对 | 改 Demo → 重新量测 → 更新锚定配置表 → 再给用户确认 |

硬性要求：

- **逐条记录，不接受“还行”“差不多”。** 用户说不清时追问到能落到具体环节或具体元素。
- **玩法类意见必须闭环到“再玩一次”。** 只改不验等于没改；用户没说“这样对了”，这一步就不算完。
- 需求与范围类的意见不要自己拍板，回到用户确认。
- 每次给用户看的 Demo 都留一个独立版本号，记录用户确认的是哪一版。

## 六、什么算“用户已确认”

满足任一条才算：

- 用户明确说可以了；
- 用户提的意见都已处理，且用户对改后版本没有再提新的玩法或布局意见；
- 用户明确授权“就按这个做”。

以下都**不算**：用户说“我看看”；用户提了意见但还没看到改后的版本；你觉得已经没问题了；用户长时间没回。

用户没回时不要自己开工。确实需要先推进时，在交付说明开头显著标出“Demo 未经用户确认”。

## 七、冻结

确认之后：

- 记下 Demo 的文件路径、版本号、确认时间、用户的结论原话；
- 锚定配置表与 Demo 一并冻结；
- **往后 Lua 版本以这份 Demo 为主要依据**：界面布局、玩法规则、数值、文案都要与它一致；
- 后续发现 Demo 本身有问题（元素放不下、规则走不通），**停下来重新出 Demo 并重新确认**，不要偷偷改数值接着写。

## 八、验收清单

* [ ] Demo 能打开、能操作、能走通完整一局
* [ ] 策划案里的可测试规则在 Demo 里都能被验证到
* [ ] 所有界面（开始 / 进行中 / 成功 / 失败 / 重开 / 其他）都在
* [ ] 玩家可见文案与策划案逐字稿一致
* [ ] 交付给用户的那份**没有任何调试显示与开发工具痕迹**
* [ ] 手机三种比例下都完整可见
* [ ] 锚定配置表已生成，每个元素都能追溯到量测结果
* [ ] 用户已经试玩并给出结论；玩法类意见已闭环到“再玩一次”
* [ ] Demo 版本号已记录，用户确认的是哪一版写清楚了
* [ ] 给用户的那段话里没有术语，也没有解释实现原理
