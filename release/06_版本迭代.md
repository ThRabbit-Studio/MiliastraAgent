# 06 版本迭代

> 本分册里凡是要对用户说的话（追问、索取、交付、汇报），都由沟通任务执行，见 `24_子代理_用户沟通.md`；执行本分册的子代理不直接联系用户。

## 一、这一步要什么

一版做完之后，用户又提了新内容或改了主意。这一步负责**把改动做进去，同时不把已经好的东西弄坏**。

**进入条件**：上一版已经跑通，用户提出了新的内容或调整。
**退出产物**：新版本 + 改动说明 + 回归结论。

## 二、先判断这是哪一种改动

不同类型要走的路完全不同。**判断错了，要么白白重做一遍，要么把玩法改乱。**

| 类型 | 判定标准 | 要走什么 |
|---|---|---|
| **窄改动** | 只改文案、数值、素材，或修 bug；不动界面结构、不动玩法规则 | 直接改。策划案里对应条目同步更新；跑与该改动相关的用例与回归 |
| **小扩展** | 加一个界面元素、加一段内容、加一个已有的机制变体；核心玩法不变 | 改策划案 → 更新用例 → Demo 里加上 → 冻结 → 改代码 |
| **重大玩法更新** | 换或加核心玩法、加整块界面、界面结构性重排、平台基准变化 | **完整重走**：编策划案 → Demo 初审 → 编写 Lua。禁止跳过 Demo |

判断不了按“重大”处理，先问用户要不要出新版 Demo。

**重大更新的清单**（满足任意一条就算）：

- 新增或替换核心玩法（例如从纯解谜变成带战斗的解谜）；
- 新增整块界面区域或整页新界面；
- 已有界面发生结构性重排（元素增删、分区调整、主次变化）；
- 设计基准或目标平台发生变化；
- 用户明确要求“先给我看看新版长什么样”。

## 三、改动时要同步维护的东西

改代码的同时，下面这些必须一起更新，否则下一次迭代就会拿到错的依据：

| 东西 | 什么时候改 |
|---|---|
| 策划案 | 规则、数值、文案、界面任何一项变了就改 |
| 验收用例 | 规则变了先改用例，再改实现。**不允许实现改成什么样、用例就跟着改成什么样** |
| 网页 Demo | 走 Demo 的改动类型时；Demo 是最终呈现的依据，不能落后于代码 |
| 锚定配置表 | 任何位置或尺寸变化 |
| 架构说明 | 文件划分、模块职责、挂载关系有变化时 |
| 版本号 | 每次给用户看的版本都要留号 |
| 项目状态记录 | 每完成一轮就更新 |

**版本号规则**：每次交给用户的版本单独记一行——版本号、日期、用户看的是哪一版、用户说了什么、这一版和上一版的差别。

## 四、回归

- 改动后**必须重跑受影响的旧用例**，只跑新用例不算回归。
- 改动碰到共享逻辑（运行时、输入、布局换算、日志收口）时，要确认与之相连的功能没被改坏。
- 布局改动后，按 `00_主控与派单.md` 3.2 的分辨率矩阵重新走一遍，确认手机三列仍然完整可见。
- 真机相关的改动，没在真实环境看过就如实标注，不许写成“已验证”。

## 五、怎么跟用户交代

对萌新用大白话，只说这四句：

```Plaintext
1. 这一版多了什么 / 改了什么
2. 你要做什么（要重新做什么操作，按顺序写；不用你做就写“不用你做什么”）
3. 怎么玩（操作和目标）
4. 还有什么没做
```

对大佬可以附带参数表、改动清单与接口变化。

**不要**把内部工作过程、检查记录、文件角色讲给用户听。

## 六、验收清单

* [ ] 改动类型判断正确，并写明了依据
* [ ] 属于重大更新的，已经重走策划案与 Demo，且用户重新确认过
* [ ] 策划案、用例、Demo、锚定配置表、架构说明中受影响的部分都同步更新了
* [ ] 规则变化是先改用例再改实现，不是反过来
* [ ] 受影响的旧用例已回归
* [ ] 多端矩阵重新走过，手机三列完整可见
* [ ] 新版本号已记录，用户看的是哪一版写清楚了
* [ ] 给用户的白话说明只讲了四件事，没有术语
* [ ] 没有在迭代里顺手修无关的毛病（要修就单独走 Bug 修复）
