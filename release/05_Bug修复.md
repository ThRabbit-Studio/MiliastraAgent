# 05 Bug 修复

> 本分册里凡是要对用户说的话（追问、索取、交付、汇报），都由沟通任务执行，见 `24_子代理_用户沟通.md`；执行本分册的子代理不直接联系用户。

## 一、这一步要什么

把已经出现的故障**定位到根因，再用最小改动修掉**。

**进入条件**：有可观察的故障现象，以及复现条件或日志。
**退出产物**：修好的文件 + 根因链条 + 回归结论 + 一份归档文档。

**目标不是“让现象消失”**，而是先把根因落到具体依据上。没有根因就改代码，等于猜。

## 二、先按现象定位

拿到故障后先到 `12_参考_故障案例库.md` 按现象查一遍：这个现象是不是已经记录过的高发机制。**查得到就直接用那里的正确做法，不要从头重新推断。**

## 三、不向用户要任何前置条件

- 不发送编辑器操作步骤，不索取控件模板索引、容器节点索引、脚本名称。
- 不要求用户重新建容器、重新挂脚本、重新校准。
- 需要的配置与身份信息**从已存在的代码与工程文件里读**；读不到的记为“缺少依据”，写进报告的未解决项，**不许用猜的值填空后继续改**。
- 需要用户配合时，只允许两件事：**说清现象与怎么操作才出现**、**把报错的那段文字整段发来**。

对萌新说这两件事时用大白话：

> 出错的时候会跳出一段文字，把它整段复制给我就行。
> 顺便说一下：你点了什么、走到第几步出现、是每次都有还是偶尔。

## 四、排查顺序

**第一步：分类。** 任何故障动手之前先归入下面一类，并写明判断依据：

| 类别 | 典型表现 | 先看什么 |
|---|---|---|
| 配置类 | 编号缺失、格式不对、脚本没挂上 | 代码里的配置区、启动汇总 |
| 启动竞态类 | 偶发失败、第一次进关卡报错、切场景后报错 | 就绪记录、重试次数与最后原因 |
| 接口用法类 | 调用报错、字段写不进、行为与文档不符 | 当前 API 文档、报错原文与调用栈 |
| 逻辑类 | 数值算错、走了错分支、内容不显示但不报错 | 代码走查、本地复现 |
| 表现与适配类 | 位置偏、被裁切、多端不一致、图片显示异常 | 对照 Demo 的量测、锚定配置表、真机画面 |

**第二步：复现。** 按顺序尝试，并如实记录结论：

1. 读用户回传的报错文本（首选）；
2. 代码走查复现（数值、分支、条件判断类有效）；
3. 本地逻辑复现（只对不依赖编辑器接口的纯计算有效，不等于真机复现）；
4. 最小探针（只验文档已声明、行为仍不确定的单个问题，用完删掉）；
5. 请用户复现并回传（前四项都拿不到证据时用，一次只索取一次信息）。

- 复现条件必须写清：走到哪一步、点了什么、第几次出现、和分辨率或设备有没有关系。
- **偶发故障**要记出现频率与最后未就绪原因、重试次数，不能只写“有时候会”。
- 复现不出来时，**不得推断修复有效**，结论保持未确认。

**第三步：写链条。** 写出“现象 → 直接原因 → 根因”。链条断了就回去补证据，不许跳。

**第四步：回查接口。** 把涉事标识在当前 API 文档里逐项核对；没找到依据就不许改它。

**第五步：最小补丁。**

## 五、最小补丁

- 只改与故障直接相关的最小范围；相邻问题只记录，不顺手修。
- 不做顺带重构、顺手格式化、批量改名。
- 一次只改一个变量；同一处连续两次没修好，停下来重新分析，不许继续试参数。
- 改动前保留原文件或原片段，保证能一键还原。
- 补丁里不许留调试残留、临时开关或注释掉的旧代码。
- 修完之后，改动的每个接口标识都要重新回查文档。

**改什么，不改什么：**

| 故障类型 | 改这个 | 不是改这个 |
|---|---|---|
| 布局类 | 锚定配置表对应行 + 代码（两边必须同时改） | 只改代码让表失真 |
| 启动竞态类 | 就绪判断逻辑本身 | 加长等待时间或加多试 |
| 输入类 | 事务与去重逻辑 | 时间间隔、冷却、标志位 |
| 图片类 | 资源来源与绑定顺序 | 加遮罩或占位图盖住 |
| 坐标命中类 | 坐标关系或架构选择 | 把某台设备上试出来的偏移硬编码进去 |
| 接口用法类 | 调用形式本身 | 保留旧写法再补一层兼容 |

**禁止**用调大数值、加长等待、多加重试、把报错包住后继续跑、注释掉逻辑、临时删功能这些方式绕过故障。注意区分：在完整事务入口捕获异常后**立即进入失败状态并停止后续逻辑**是必须的错误边界；捕获后照样往下跑才是被禁止的绕过。

## 六、规则类故障：先有失败用例，再修

计分、胜负、冷却、碰撞边界、暂停与重开、输入语义、服务端变量与信号，走“失败用例 → 最小修复 → 用例转通过 → 回归”的顺序：

```Plaintext
1. 先复现，或先把缺陷写成一条最小失败用例：前置状态、玩家动作、期望结果、失败边界
2. 确认输入语义：这条用例描述的输入，在代码里对应哪个状态与哪次事件
3. 只做最小修复，一次只改一个变量
4. 跑目标用例确认转通过，再跑受影响的旧用例做回归
```

- **不许先改实现，再补一条永远为通过的断言。**
- **不许因为用例失败就删掉或跳过它。**
- **不许用日志断言证明体验类结论**（好玩、手感好）。体验问题先把主观描述转成 1–2 个可比较的参数，存基线后再调，一次只改少量变量。
- 用例不复制生产算法。

## 七、常见高发故障的定位入口

完整索引与每一类现象的根因、正确做法都在 `12_参考_故障案例库.md`。**先在那里按现象定位，再回到对应分册看正确做法**，不要从头重新推断。

本节不重复那张表，避免出现两份说法。

## 八、收尾

修完之后按顺序做四件事：

1. 跑语法检查（按 `23_子代理_语法检查.md` 派任务），问题清单逐条处理；
2. 重走一遍原始复现步骤，确认**现象消失**，而不是只确认不再报错；
3. 做回归：故障涉及共享逻辑（运行时、输入适配、布局换算、日志收口）时，确认相连的功能没被改坏；
4. 写归档文档。

### 归档文档（每个 bug 一份）

**每修掉一个 bug 都要留一份**，一次修了三个就写三份，一份只讲一个。

- 文件名：`YYYYMMDD_千星2D_关于xxx的问题.md`
  - `YYYYMMDD` 是**修复完成**的日期；`xxx` 是 8–16 个汉字的简短描述，用问题本身命名，不用编号、不带日期、不含 `\ / : * ? " < > |`。
- 位置：当前用户「文档」目录下的 `千星2D开发` 文件夹，例如 `C:\Users\<用户名>\Documents\千星2D开发\`。文档目录被重定向到别处时，以系统实际的文档路径为准；文件夹不存在先创建；写不进去就把全文与建议路径写进报告，不得省略。

内容结构：

```Markdown
# 20260418_千星2D_关于存档索引错位的问题

## 一、问题表现
- 现象：<玩家能感觉到的说法>
- 出现条件：
- 复现步骤：1. … → 2. … → 3. …
- 出现频率：必现 / 偶尔
- 影响范围：

## 二、出现原因
- 直接原因：<具体到文件、函数、字段或某一行>
- 根因：<为什么会形成这个直接原因>
- 定位依据：<日志片段 / 代码位置 / 文档条目>

## 三、解决方法
- 改动文件：
- 改动内容：
- 为什么这样改：
- 排除的方案：
- 是否可回退：

## 四、验证情况
- 语法检查：
- 复现验证：
- 真机验证：<通过 / 待验证 / 不适用；不是通过时写清待验证项>
- 回归结论：

## 五、备注
- 同类风险：
- 相关条目：<关联的其他归档文档，没有写“无”>
```

写作要求：一个 bug 一份文档；表现只写可观察的事实，推测只能出现在原因的排除过程里；原因要能指到具体的文件、函数、字段或那一行；诚实标注验证状态，没在真实环境复现过就写“待验证”；保留历史文档，不覆盖旧记录。

## 九、修复报告

按下面 12 项写（技术部分照实写）：

```Plaintext
1. 现象（表现 + 出现条件 + 复现步骤 + 频率）
2. 类别（配置 / 启动竞态 / 接口用法 / 逻辑 / 表现与适配 / 未确认）与判断依据
3. 复现结论（已复现 / 未复现 / 复现条件不明，注明是编辑器内、日志推断还是本地复现）
4. 直接原因（具体到文件、函数、字段或某一行）
5. 根因
6. 证据（日志片段、文档条目、量测值；每条标注来源与真机状态）
7. 修复方案（改了什么、为什么这样改）
8. 为什么不是别的方案（被排除的候选原因与排除依据）
9. 影响范围（是否影响其他功能、多端呈现、锚定配置表）
10. 验证情况（语法检查、复现验证、真机验证，分别标注）
11. 未解决项（仍待确认的部分、读不到的配置依据、刻意不改的相邻问题）
12. 本次产出的归档文档（文件名与完整路径）
```

**另外给用户一份白话说明**，只讲三件事：出了什么问题（用玩家能感觉到的说法）、我改了什么现在是什么情况、你还需要做什么（按顺序的点按步骤；没有就写“不用你做什么”）。日志原文、错误码、函数名属于技术部分，不要塞进给用户看的那一段。

**没有在真实环境复现过的修复，只能说“已修改，待验证”**，不许写“已修复”“问题已解决”。

## 十、必须停下来的时候

| 情况 | 处理 |
|---|---|
| 现象说不清，用户只说了“报错了” | 只问现象、怎么操作才出现、报错文字这三件事 |
| 拿不到报错文字，也没有任何可观察现象 | 再要一次获取方式；仍然拿不到就把结论保持未确认，不许猜修 |
| 复现不出来且没有其他证据 | 说明无法复现，列出已排除项与下一步建议，不声明修好了 |
| 根因落在文档没写明的能力上 | 停止修复，标记未确认，说明文档缺什么 |
| 代码里读不到修复需要的配置 | 记为未解决项并说明缺什么，不许向用户发起一轮交接 |
| 修复要动超过 3 个文件或需要重写结构 | 停下来说明范围，请用户确认是否扩大或改走编写流程 |
| 同一处连续两次没修好 | 停止试错，重新分类 |
| 同一故障三次尝试都失败 | 停止修改，重新分类并列出证据缺口 |
| 需要用户配合操作 | 先取得用户明确同意，且只索取现象与报错文字 |

## 十一、验收清单

* [ ] 故障已分类，并写出了判断依据
* [ ] 先复现或先建了最小失败用例，再动手改
* [ ] “现象 → 直接原因 → 根因”链条完整，没有断点
* [ ] 涉事标识已在当前 API 文档里回查过
* [ ] 补丁范围最小，没有夹带重构、格式化或无关文件
* [ ] 布局类修复同时更新了锚定配置表
* [ ] 没有用调大数值、加长等待、多加重试、包住报错继续跑等方式绕过
* [ ] 原文件或原片段已保留，可一键还原
* [ ] 语法检查已执行并处理完问题清单
* [ ] 已重走复现步骤，确认现象消失而不只是不再报错
* [ ] 回归已完成；共享逻辑与相邻功能没被改坏
* [ ] 归档文档已生成，文件名与存放位置符合规定
* [ ] 修复报告 12 项齐全；对用户的白话说明里没有术语
* [ ] 没有把“已修改、待验证”写成“已修复”
