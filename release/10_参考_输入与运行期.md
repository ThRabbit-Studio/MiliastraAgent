# 10 参考：输入与运行期

写运行期逻辑、排查“没反应 / 不动 / 不刷新”时读这一份。

## 一、受约束的运行环境

编辑器里的 Lua 与通用 Lua 不完全一样。动手前从当前 API 文档核对：

- Lua 版本与语法边界；
- 可用、被裁剪或被替换的标准库；
- 调用栈、时间、数学等扩展能力；
- 文件系统、网络、动态模块与原生对象构造是否开放；
- 是否支持按路径加载模块，路径规则、模块名规则、加载时机与失败行为；
- 是否提供计时器，以及它属于哪个时间域、怎么取消。

**文档没有声明的能力一律视为不可用。** 没有文档化计时器时，计时由运行时用逐帧时间源加队列实现，不要凭空调用常见框架里的定时器。

## 二、把状态映射到原生控件

画面由 Lua 状态驱动编辑器提供的原生控件。图片、文字、滚动文字、输入区域、按钮、运行时父组分别需要哪种控件，按当前需求查文档。

控件通常来自用户预先建立的客户端控件模板；用户给的是模板“索引”。实例化怎么写、父级参数收对象还是标识、返回什么类型，都要查文档。**模板索引、运行时实例编号、父级控件、图片来源与图片编号是四个不同概念，不得互换。**

## 三、按生命周期组织代码

脚本由编辑器的生命周期驱动，**不要从文件顶部启动永久循环**。

- 初始化阶段处理不依赖完整控件树的本地状态；
- 启动阶段取得宿主并构建内容；
- 启用与启动可能衔接，启动函数要**可重复执行**，避免重复创建与重复注册；
- 停用时暂停或取消本次工作：关闭输入与逐帧、注销自有监听、停止动画；
- 销毁时做最终清理，重复调用不产生额外效果。

**创建控件、注册监听、启用逐帧时是否会同步重入**，必须以文档和真实观察为准。文档没说明时记为未确认，用状态 guard 防止重复进入。

**本项目已在真实环境观察到：实例化客户端控件会同步重入挂载脚本的启动回调。** 重入时环境独立，且状态可能仍是初始状态，只靠「只在初始状态才启动」的单一标志挡不住。因此创建类调用必须同时具备跨实例的初始化防线（初始化锁，或「宿主控件树里是否已存在本页面」的检测）。除这条已观察到的机制外，其余重入仍按未确认处理。

**生命周期回调发生过，只能证明脚本进入了该回调**，不能证明所有外部对象和数据都已就绪。挂载容器、脚本查询结果、画布信息要分别判断。

### 启动就绪必须分三类

| 结果 | 判定 | 处理 |
|---|---|---|
| 配置错误 | 用户提供的配置缺失或格式不对 | 立即报明确错误，不做无意义的上百次重试 |
| 尚未就绪 | 运行时对象还没出现或还没存活 | 记录原因，在后续已文档化的回调里**有限重试**，只结束本次尝试，不进入失败、不创建资源、不开放输入 |
| 确定不匹配 | 对象已就绪但身份明确不符 | 立即失败，不再重试 |

**三类不得混在一起判断**，偶发故障多半出在这里。重试要有预算、有触发入口、有停止条件，并记录已尝试次数与最后一次未就绪原因。

`pcall` 的第一个返回值只表示“有没有抛错”。被调用函数若返回 `false, 原因`，要接成“有没有抛错 + 是否成功 + 原因”分别判断，**不能拿第一个返回值当“启动成功”**。

## 四、状态机

```Plaintext
NEW → STARTING ↺ → RUNNING
STARTING 或 RUNNING → FAILED
任意状态 → DESTROYED
```

- `NEW`：尚未启动；
- `STARTING`：先验证静态配置，再分别等待启动依赖就绪；全部就绪并完成身份核对后才创建资源；
- `RUNNING`：推进玩法；
- `FAILED`：停止逐帧逻辑，执行清理，只输出一个聚合故障块；
- `DESTROYED`：执行最终清理，重复调用无副作用。

“运行标志”用于阻止同一主故障重复输出。

**安全启动顺序**：

```Plaintext
状态改为 STARTING
→ 验证用户提供的配置是否完整且格式有效
→ 分别探测脚本上下文、挂载容器及其他启动依赖
→ 任一依赖尚未就绪：记录原因并在后续已文档化回调中有限重试
→ 全部就绪：核对挂载关系；确定不匹配才进入 FAILED
→ 创建本次玩法资源
→ 每个资源创建成功后立即登记清理动作
→ 状态改为 RUNNING
→ 让已启用的启动就绪回调开始进入玩法分支
→ 通过普通日志入口输出一次启动汇总
```

启用逐帧做就绪重试时，**该状态下只允许执行一次就绪尝试，禁止推进玩法**；玩法专用回调要先进入 `RUNNING` 再启用。

## 五、输入

### 5.1 手柄导航的默认行为

- **默认方向导航**：控件开启“可被手柄摇杆导航选中”后，编辑器会默认启用内置方向导航——摇杆给方向时，自动选中该方向上距离最近的控件。方向判断与目标选择由编辑器完成。
- **当前聚焦控件**：同一时刻全局只有一个。方向导航以它为起点；没有聚焦控件时，手柄导航输入通常不会被界面消费。
- **导航隔离区域**：开启“隔离手柄导航”的容器会形成独立区域，“距离最近”只在区域内搜索；不属于任何隔离区域时，整棵控件树参与搜索。
- **导航事件**：一次摇杆方向输入既可能参与默认聚焦移动，也可能产生对应方向事件，两者来自同一次输入。确认与取消事件只发给当前聚焦控件，且不会自动执行业务。
- **聚焦控件被销毁**：运行时会清空当前聚焦并让它退出聚焦，**不会自动选择下层界面的其他控件**。

### 5.2 坐标域互不相通

输入事件位置、无事件时取得的位置、控件布局位置、画布尺寸、玩法逻辑位置，**可能来自不同坐标域**。名称相似、数值接近，都不能证明它们有相同的原点、方向、单位、缩放或作用范围，也不能证明可以直接比较或换算。

“由编辑器判断某个控件是否被命中”和“脚本读位置自己算命中”是两种不同架构：前者不依赖坐标换算；后者只有在相关关系已由文档明确、或有真实证据时才成立。

### 5.3 输入架构三选一

| 优先级 | 架构 | 什么时候用 | 禁止 |
|---|---|---|---|
| 1 | **原生控件命中（默认）** | 只需要知道点击、进入、离开、拖拽发生在哪个区域 | 不要在这些区域上方无条件再放一个开启命中的全屏区域 |
| 2 | **统一逻辑命中（有条件）** | 玩法确实需要脚本自己判断位置，且输入、布局、画布与玩法坐标之间的关系已经明确 | 任一必需关系未确认时不得选它 |
| 3 | **混用** | 只有真实验证过命中顺序、穿透与单次动作去重之后 | 未验证就混用必然出现重复触发或抢事件 |

需要背景输入时，用不重叠的区域，或先用一次真机验证证明穿透与同级顺序符合预期。

### 5.4 运行、可见、命中是三个状态

| 逻辑状态 | 参与运行 | 画面可见 | 接收输入 |
|---|---|---|---|
| 正在显示的非交互图片 | 是 | 是 | 否 |
| 可交互按钮或命中区 | 是 | 按真实类型决定 | 是 |
| 半初始化或失败对象 | 不应继续推进 | 否 | 否 |

- **隐藏顺序**：先关闭输入命中 → 再隐藏 → 必要时停止对象运行。
- **显示顺序**：先启用对象 → 按文档或真实证据重提会被重置的属性 → 再显示 → 最后开放输入命中。

### 5.5 坐标实现约束

- 需要位置或自定义命中时，在启动与画布变化时用文档声明的画布尺寸查询能力。宽高只有**同时满足文档数值契约且是有限正数**时才有效。
- 初次查询无效不证明永久失败：记录“画布尚未就绪”，关闭玩法输入、保持未进入 `RUNNING`，在后续已文档化回调里按**明确配置的有限预算**重试；不得阻塞循环、不得每次各打一条日志。预算耗尽才进入失败，并一次性报告尝试次数与最后结果。
- 运行中尺寸暂时无效时同样暂停输入并有限重试，**禁止继续拿旧尺寸处理新事件**。
- **禁止把屏幕分辨率、经验尺寸或猜测值当画布尺寸。**
- 需要保存的坐标字段：画布宽高与就绪状态、重试次数与预算、缩放比例与视口边界、事件位置契约、轮询位置契约（仅在文档支持轮询且玩法需要时）、位移契约、契约证据与验证错误。
- 坐标语义仍未确认时，按顺序处理：① 只用原生命中、不读位置的方案；② 拖拽按触点身份维护按下/移动/释放事务；③ 只在实际出现坐标错乱且用户明确同意时才做专项调试；④ 确需仿射求解时用三个不共线样本加一个独立验证样本，结果只能记为项目侧推断，验证通过后才算确认。
- **禁止**把输入位置直接与布局位置、布局尺寸、画布边界或玩法边界比较；禁止把输入位移直接加到布局位置；禁止把画布宽高当作输入坐标原点的证明。
- 确实需要换算时，换算只允许集中在一个输入适配层里，并且渲染、命中、拖拽与界面必须共享同一套逻辑坐标定义。

### 5.6 一次物理操作只产生一次动作

```Plaintext
按下语义：归一化当前位置与按下位置；捕获活动触点与命中目标
拖拽开始：只有同一事务可以进入拖拽；只发送一次
拖拽移动：只有同一事务可以更新；坐标关系已确认时优先用绝对位置，位移只作单次增量
拖拽结束：只发送一次并释放捕获，不额外产生单击
释放语义：结束按住状态；只有没形成拖拽且满足规则时才生成一次单击
完成/单击：若另有完成事件，用事务序号去重，不得重复执行动作
进入/离开：只更新悬停；离开绝不自动产生单击
```

支持多触点时按触点身份各维护一条事务；不支持时也要忽略非当前活动触点的事件。脚本被停用、失败或销毁时，**显式丢弃未消费的输入**，防止恢复后补发旧操作。

## 六、日志

- 普通信息与错误分开走不同的入口；具体入口名称与副作用从当前 API 文档确认。
- 每条日志带脚本或模块前缀；同一条只打一次；**不逐帧刷屏**（逐帧日志只允许启动前几帧或低频心跳）。
- 只在完整的**事务边界**（启动、逐帧更新、清理）建立错误边界，不要给每个取值赋值单独套保护调用。
- 致命故障只输出**一个连续块**：

```Plaintext
GAME FAULT BEGIN <错误码>
  phase: <阶段>
  message: <原因>
  object: <对象或 nil>
  evidence: <来源>
  traceback: <调用栈文本；取不到写“不可用”>
  cleanup[1..n]: <清理错误，只追加，不覆盖首个错误>
GAME FAULT END <错误码>
```

启动汇总与故障块至少包含：容器索引、预期脚本短名称、实际取得的脚本名称、运行状态、阶段、首个错误、调用栈、聚合后的清理错误。文档没有提供的运行时信息写“未确认”，不要虚构字段。

**日志实现骨架**（只规定职责与顺序，具体接口查文档）：

```Plaintext
配置
  容器索引 = 用户提供的真实值
  预期脚本短名称 = 从用户给的名称或路径归一化得到
  锚定配置表 = 来自 09 第七节

运行时
  状态 = NEW；主故障是否已输出 = false；清理栈 = 空
  启动就绪尝试中 = false；已尝试次数 = 0；重试预算 = 有限正整数；最后一次未就绪原因

启动事务
  状态改为 STARTING
  先验证配置与锚定配置表；缺失或格式错误立即失败
  发布完整的重试状态与重入 guard
  启用只推进就绪检查的回调

每次就绪尝试
  分别取得当前脚本实例、挂载容器与挂载查询结果
  暂未就绪：记录原因与次数，本次结束
  达到预算：只输出一个聚合故障
  全部就绪：核对短名称一致、容器查到的实例就是当前实例
  明确不符：立即失败，不重试
  创建资源（按锚定配置表设置锚点、中心点、位置与尺寸），创建成功立即登记清理
  状态改为 RUNNING，输出一次启动汇总

逐帧事务
  STARTING 时只推进一次就绪尝试；仅在 RUNNING 时推进玩法；整个事务共用一个错误边界

失败事务
  同一主故障只进入一次；保存首个错误、阶段、状态与调用栈
  状态改为 FAILED；停止输入、加载与逐帧
  按清理栈反向释放；清理错误只收集不逐条打印
  生成带 BEGIN/END 的连续故障块，一次性输出

销毁事务
  重复调用无副作用；停止逐帧并反向执行剩余清理
  若清理失败且此前没有主故障，输出一个聚合故障块；状态改为 DESTROYED
```
