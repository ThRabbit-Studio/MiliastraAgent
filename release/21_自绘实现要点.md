# 21 自绘实现要点：帧动画与像素拼图

> **先看这条：这件事现在有工具了——工具优先，但执行派给 `25` 号任务。**
> `tools/qx2d` 的 `pixel` 与 `frames` 两条命令能完成像素画与帧动画还原，自带独立校验，默认输出 JSON 数据（需要 Lua 时加 `--emit lua`，见 `tools/README.md`）。
> **主控不亲自跑工具**：把输入、输出目录、参数与 CONFIG 常量写进任务书，派 `25_子代理_像素画与帧动画.md` 这**一个** Agent 执行；`ok=true` 才采用产物。
> 非像素风的照片 / 立绘用 `tools/qx2d shapes` 做图元拟合；调运动曲线、时长与事件用 `tools/qx2d anim`（输入是关键帧文档）。`n> 只有工具不可用、报 `ok=false`（退出码 2）且按允许的参数重试一次仍不达标，或需求正落在工具不具备的能力上（overpaint 分层、接入已有脚本、I/P 帧差分、父节点共同运动、运行时验证）时，才按下面的要点自绘简化版。

## 一、这份文件解决什么

本目录**没有**动画还原与像素重建技能，也**没有**可检索的图片资产清单。工具用不了时，按这里的要点**自己实现简化版**。

**先跟用户说清楚能做到什么程度。** 简化到什么水平、损失多少还原度，取得用户同意再动手。

## 二、动手前先算控件数量

一个 64×64 的像素角色逐色块拼出来可能是几百个控件。**不要先写完再发现超限。**

估算办法：

```Plaintext
单帧矩形数 = 把画面按同色矩形合并后的矩形个数（控件数的下界）
单帧控件数 ≈ 单帧矩形数 × 复用系数（1.0～1.5）
峰值控件数 = 所有帧里控件数最多的那一帧，不是各帧相加
```

超出同屏预算时的降级顺序：**先减帧率 → 再减颜色数 → 再减画布分辨率 → 最后砍非核心特效**。砍掉什么要写进交付说明。

## 三、通用要点

- **先量化需求**：目标画布尺寸、格子大小、帧率、总帧数、是否循环、控件数量上限、允许的误差。没定就先定。
- **图片元素当矩形用**：一个可拉伸的图片元素就是任意宽高的矩形。同色区域越大、越方整，用到的元素越少。
- **颜色先收敛成一张调色板**（建议不超过 32 色），每个元素用调色板里的颜色着色；零散取色会让数量失控。
- **优先合并与复用**：能用一个矩形盖住的区域不要拆成两个；相邻同色矩形要合并；能靠父级整体移动的，不要逐个改子元素位置。
- **先做静态、再做时间轴**：先让一帧正确显示，再叠加时间维度。一帧都没摆对就做动画，等于把两个问题叠在一起排查。

## 四、像素拼图（静态画面）

1. **取点阵**：把参考图解码成 RGBA 点阵，统一到同一宽高，左上角为原点，x 向右、y 向下。记录原图哈希，避免中途换图后结论失效。
2. **固定三份数据**：`原图`、`规范目标点阵`（按目标网格重采样后的结果）、`量化目标`。验收基准是**规范目标点阵**，不是量化目标。
3. **量化**：把颜色映射到调色板。允许误差时给出阈值（例如 RGB 各通道最大差 ≤ 3）；要求无损时不量化，调色板就是实际用到的颜色。
4. **同色矩形合并**：对每种颜色的掩码，先把水平连续像素并成行段，再把相邻行中同起点、同宽、同色的行段垂直并成矩形。合并收益不明显时就停手。
5. **分层**：按绘制顺序排序。大块底色先画、细节后画，能用一块底色打底就不要逐块拼。
6. **生成绘制记录**：每条至少是 `颜色 | x | y | 宽 | 高 | 层级`，记录流要能独立恢复整幅画面。
7. **验证**：按绘制顺序把记录栅格化，与规范目标点阵逐像素比对，统计差异像素数、最大通道误差与平均误差。要求无损时这些必须为 0。

## 五、帧动画（时间轴）

在静态结果之上叠加：

1. **统一帧网格**：所有帧解析成同一宽高的点阵，记录每帧时长、循环方式、帧率、源尺寸与哈希。
2. **按帧拆矩形**：每帧做一遍第四节的合并，得到逐帧的矩形集合。
3. **提取时间冗余**，三种都要考虑：
   - **静态背景**：整段都不变的区域只在启动时创建一次，让动态元素盖在它上面，不要每帧重画；
   - **共同运动**：一组矩形共享同一个平移/缩放/旋转时，给它们建一个空父级，播放时只改父级变换；
   - **动态残差**：先对相邻帧做运动补偿，再算真正变化的区域，只把补偿后仍不同的部分转成动态矩形。
4. **建立元素池与轨迹**：给相邻帧的矩形配成稳定槽位。配对优先级是「状态完全相同 → 只变色 → 只移动 → 移动+缩放 → 离场者让位给入场者 → 离场隐藏 → 入场从池中取新槽位」。**池大小取任意时刻同时占用的最大槽位数**，不是各帧元素数之和。
5. **播放期零创建零销毁**：元素在启动阶段一次性建好并预热，播放阶段只改属性（位置、尺寸、颜色、显隐）。
6. **只改变化的属性**：为每个槽位缓存当前状态，值与缓存相同就跳过这次写入。
7. **数据编码（体积敏感时再做）**：先上「全部槽位初始状态 + 只记变化」的结构；再按槽位编号差分、对位置尺寸与颜色做帧间差分、对无变化的时间段做游程压缩。**编码前先比较几个候选方案的最终体积**，包括播放器本身的开销——有时「每帧直接写绝对状态」更小也更简单。
8. **验证**：用一个**独立**的解码实现把数据还原成时间轴，逐帧比对帧时长、槽位、可见性、颜色、位置、尺寸；再按绘制顺序逐帧栅格化，与参考帧比较差异像素数与颜色误差。**独立验证器不得复用编码器的函数。**

## 六、落地时的性能约束

- **单帧创建量有上限**：元素池较大时不要在第一帧一次性建完，改成分帧预热并显示进度，全部就绪后再一次显示。
- **播放期只改属性**：一帧跨过多帧时，只把每个槽位的最终状态应用一次，不要逐帧追赶。
- **循环动画用累计时间取模**，避免每圈累积浮点漂移。
- **用父级承载共同运动前**，先用一个父级加一个测试子元素验证：父子都显式激活并显示，子元素确实可见、父级变换确实带动子元素。不成立就退回「全部直接挂到主节点的完整静态图」，不要留下只画了背景的半成品。
- **不要用元素当布局容器**：文字和图片挂在图片元素下面可能不显示；要分层就用透明容器分别承载。

## 七、交付时怎么写

- 写清控件数量、脚本体积、误差、降级了什么。
- 这些数字都是**静态统计与本地比对**的结果，**真机状态一律是“待验证”**；只有在真实环境里看过才能记为“已通过”。
- 用户没同意简化程度之前，不要直接进正式脚本。
