# 07 最终交付

> 本分册里凡是要对用户说的话（追问、索取、交付、汇报），都由沟通任务执行，见 `24_子代理_用户沟通.md`；执行本分册的子代理不直接联系用户。

## 一、这一步要什么

把做完的关卡整理成**用户能自己装上、自己玩、玩不明白时知道找谁**的一整套东西。

**进入条件**：内容做完，验收用例全部通过，已知故障都已收口。
**退出产物**：交付包 + 挂载说明 + 已知限制 + 真机验证结论。

## 二、交付包里必须有什么

| 内容 | 说明 |
|---|---|
| **代码文件** | 单文件就是一个入口脚本；多文件是整个代码目录，含入口与各模块 |
| **挂载说明** | **必须单列一节**。脚本挂载关系不会随资源包一起带走，用户必须自己挂一次 |
| **需要用到的素材编号** | 图片、动效、音频各自列出编号与用途，便于用户核对 |
| **需要用户在编辑器里填的配置** | 控件名称与相对路径、模板索引等；每项写清去哪儿读、缺失时会怎样 |
| **测试结果** | 跑过哪些用例、结果如何、有哪些是待验证 |
| **已知限制** | 目前做不到的、简化掉的、只支持某些情况的 |
| **给用户的操作说明（白话版）** | 见第五节 |

**交付说明的技术部分**按下面写：

```Plaintext
1. 这次交付了什么（对应策划案的哪些内容）
2. 文件清单与各自角色
3. 与网页 Demo 的一致性结论（布局、规则、数值、文案）
4. 验收用例与结果汇总
5. 用到的编辑器接口与文档依据
6. 资源所有权与收尾方式
7. 素材编号与来源
8. 玩家可见文本清单
9. 证据状态与真机状态
10. 未完成项、已知限制与建议的下一步
```

## 三、挂载说明怎么写

挂载是**唯一必须由用户动手、且漏了就完全跑不起来**的一步，所以要写成一步一行的点按步骤，萌新模式下一句术语都不要：

> 最后一步，把脚本装到界面上：
>
> 1. 打开「千星沙箱」
> 2. 打开「客户端脚本资源管理器」，确认里面已经有这些脚本：<逐个列出>
> 3. 回到「原神」窗口，打开「界面控件组管理」
> 4. 找到你之前建的那个「客户端控件容器」，点「画布设置」→「前往编辑」
> 5. 选中「容器节点」
> 6. 在右边切到「脚本」页签，点「添加脚本」，选 <脚本名>
> 7. 保存，然后进关卡试一下

多文件时补一句：哪些文件必须一起导入，不能只导一个。

## 四、真机验证

- 把完整内容、挂载说明、素材编号、已知提示一起交给用户在真实环境里试。
- 用户回传时记录：环境、操作步骤、期望与实际、截图或报错文字、能不能稳定复现。
- 真机问题先形成一条明确的复现步骤或用例，再修，修完同时做回归。
- **只有真机证据覆盖到的行为才能写“通过”。** 用户还没试的，交付状态写“待验证”，不许写成“已通过”。
- 静态检查通过、本地能跑、网页 Demo 好看，都不能替代真机结论。

## 五、给用户的那份说明

技术报告照实写；**另外给用户一份白话说明**，只讲四件事：

```Plaintext
1. 这个关卡是什么、怎么玩（一句话各一句）
2. 你要做什么（按顺序的点按步骤，一步一行）
3. 玩的时候注意什么（哪里可能看不懂、哪个按钮是干嘛的）
4. 还有什么没做、哪里我还不确定
```

- 萌新模式下不出现任何术语；必须提到编辑器界面时用界面原话，并补一句它是干什么的。
- 不解释实现原理、不列文件清单、不提检查过程。
- 不确定的地方直说“还不确定”，不要用术语把不确定包装成确定。

## 六、验收清单

* [ ] 验收用例全部通过；没通过的已收口或明确列为未完成项
* [ ] 界面的布局、规则、数值、文案与冻结的网页 Demo 一致
* [ ] 挂载说明单列成节，是一步一行的点按步骤
* [ ] 素材编号与用途逐项列出
* [ ] 需要用户填的配置逐项列出，并写明缺失时的表现
* [ ] 已知限制写清楚了，没有隐瞒
* [ ] 真机结论按“已通过 / 待验证”如实标注
* [ ] 归档文档（历史 bug 记录）都在，位置正确
* [ ] 给用户的白话说明只有四件事，没有术语
* [ ] 项目状态记录已更新为“已交付”
* [ ] 首页/入口能一眼看出怎么开始玩
